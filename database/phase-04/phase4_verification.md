# Phase 4 — Verification Methodology

Status: **Executed in full against the live Supabase project.** Directly reuses [phase1_verification.md](../phase-01/phase1_verification.md)'s baseline methodology, extended with [phase2_verification.md](../phase-02/phase2_verification.md)'s atomic-counter concurrency technique and [phase3_verification.md](../phase-03/phase3_verification.md)'s `set local role authenticated;` discipline. This document records what's specific to Phase 4.

## 1. Structural checks
`information_schema.columns` against both new tables (17 columns on `expense_floats`, 28 on `petty_expenses`), `pg_constraint` for CHECK/UNIQUE/FK definitions, `pg_indexes`, `information_schema.triggers` (including exact `action_condition` text for the `WHEN`-gated trigger), `pg_proc.prosecdef`/`proconfig` for all 6 new functions, `pg_class.relrowsecurity`, and `pg_policies` for all 8 policies. Frozen-baseline check: total table count 38 (36 from Phase 1–3 + 2 new), `md5(prosrc)` spot-checked for 8 key Phase 1–3 functions (`has_permission`, `current_organization_id`, `set_updated_at_timestamp`, `set_updated_at`, `generate_employee_code`, `generate_quotation_number`, `prevent_negative_stock`, `prevent_overpayment`) to confirm zero drift.

## 2. Test identity setup — adapted for an empty auth baseline
Unlike Phase 1–3's verification (run against a database that already had test scaffolding from prior rounds), this database had **zero** rows in `auth.users` at the start of Phase 4 verification. Direct `INSERT INTO auth.users` triggered Phase 1's `handle_new_auth_user()` auto-provisioning trigger (auto-creates a matching `profiles` row and a `user_roles` assignment from `raw_user_meta_data->>'role'`, defaulting to `'employee'`) — an initial attempt that explicitly inserted into `profiles` afterward failed with a duplicate-key error for exactly this reason, caught and corrected before any transaction committed. The corrected approach: insert `auth.users` with `raw_user_meta_data = {"role":"admin"}` for the positive-test identity (auto-provisions an admin role), and `{}` for the negative-test identity, then explicitly `DELETE FROM user_roles` for the negative identity to guarantee zero permissions regardless of whatever the `'employee'` role default happens to grant — rather than assuming that role has no relevant permission and being wrong.

## 3. `set local role authenticated;` discipline
Applied as the mandatory first statement after `begin;` in every RLS-dependent test this phase, per the standing lesson from Phase 3's verification. No repeat of that incident occurred this phase.

## 4. RLS — positive and negative, against real committed rows
Negative tests run first, against an empty table (INSERT correctly rejected via `new row violates row-level security policy`), then again against a real committed row created by the positive-test identity (SELECT returned 0 rows — RLS-filtered, not an error; UPDATE and DELETE both affected 0 rows) — proving RLS filters existing data, not just blocks fresh inserts. `settle_expense_float()` was tested as a direct RPC call by the zero-permission identity and correctly raised `permission denied for settle_expense_float` rather than silently succeeding, confirming the internal permission re-check (necessary because this function is `SECURITY DEFINER` and does not inherit table RLS — see `phase4_security.md` §3) actually fires in practice, not just in static analysis.

## 5. Numbering — `generate_float_number()`
Two direct calls in the same session returned `FLT-2026-001` then `FLT-2026-002`, confirming sequential, non-colliding output against the `FLT` counter key (first use of this key — no pre-existing `document_counters` rows for it).

## 6. Trigger-maintained derived fields
Inserted one `petty_expense` (amount 300) linked to a float with `issued_amount=1000`; confirmed the float's `spent_amount`/`balance_amount`/`status` updated automatically to `300/700/'Partially Settled'` with no explicit `UPDATE expense_floats` statement issued by the test. Then called `settle_expense_float(float, 700, ...)` and confirmed `spent=300, returned=700, balance=0, status='Fully Settled', settled_at` populated — proving both trigger entry points (`petty_expenses`-driven and `settle_expense_float`-driven) converge on a consistent result.

## 7. CHECK constraints and `ON DELETE` behaviors — all exercised with real statements
- `petty_expenses_amount_check` (`amount > 0`) and `expense_floats_issued_amount_check` (`issued_amount > 0`) — both triggered with a real `amount=0`/`issued_amount=0` insert, confirming rejection with the exact constraint name.
- `ON DELETE SET NULL` verified live for all three columns that carry it: `float_id`, `vendor_id`, `inventory_item_id` — each proven by linking a real `petty_expenses` row to a real parent row, deleting the parent, and confirming the FK column became `NULL` while the `petty_expenses` row itself survived (not cascaded away).

## 8. Organization isolation
Same 2-org technique as Phase 1–3, with one refinement: an earlier attempt used a malformed UUID literal for the second organization's id (`'...-org2'`, containing non-hex characters), which failed the `INSERT` outright — caught immediately (the transaction never committed) and corrected to a valid UUID before re-running, rather than silently proceeding with a test that hadn't actually set up a second organization. With a genuine, valid second organization and a real admin identity in it: `SELECT` on the first organization's float returned 0 rows, and a direct `settle_expense_float()` call against that float raised `expense float ... not found in this organization` — the identical error a nonexistent float ID produces, confirmed deliberately (see `phase4_security.md` §3 on why that's the correct, non-information-leaking behavior).

## 9. True concurrency — three scenarios, all with authoritative live proof
Same two-overlapping-transaction lock-hold technique as Phase 2/3 (`pg_sleep(3)` inside the lock-holding session, a second session started ~1s later that must block then proceed), with `clock_timestamp()` (not `now()`, which is fixed for the lifetime of a transaction) used to demonstrate real wall-clock blocking — Session B's completion timestamp was confirmed to fall strictly after Session A's commit timestamp in all three tests, not merely inferred from statement ordering in the script.

- **Two simultaneous `petty_expenses` inserts against the same float** (amounts 100, 150): final `spent_amount = 250`, both rows present — neither contribution lost.
- **Two simultaneous `settle_expense_float()` calls against the same float** (deltas 50, 30): final `returned_amount = 80` — the exact scenario the settlement-concurrency fix (`phase4_architecture.md` §5) was built to prove safe, now verified under genuine lock contention rather than static analysis alone.
- **One settlement concurrent with one petty-expense insert against the same float** (delta 20, insert amount 40): final `spent_amount = 290, returned_amount = 100, balance_amount = 610` — both writers' contributions present regardless of which acquired the row lock first.

## 10. Cleanup verification
All test artifacts (2 `expense_floats`/`petty_expenses`-related test rows sets, 1 test employee, 1 test vendor, 1 test inventory item, 1 test organization, 3 `auth.users` + their cascaded `profiles`/`user_roles`, and every `security_audit_log` row referencing the 3 test identities) removed and confirmed via live queries: **0 remaining** in every category, including 2 additional `security_audit_log` rows generated by the cleanup's own `user_roles` deletion (the still-active test identities' role removal fired the same audit trigger that logged their original assignment) — caught by running the audit-log cleanup query *after* the role deletion, per the standing FK-ordering lesson from Phase 1/2. Production data (1 real organization, 0 real floats/expenses/employees/auth users at time of verification) confirmed byte-for-byte unchanged before and after.

## 11. What this methodology does not (yet) cover
Same caveats as Phase 1–3: no UI-driven verification (frontend still unwired to Supabase), no load/performance testing. Additionally specific to Phase 4: the raw-`UPDATE`-bypass gap around `returned_amount` (`phase4_security.md` §5) is a documented architectural decision, not something this verification pass attempts to close or disprove — it was evaluated and deliberately deferred, not overlooked.
