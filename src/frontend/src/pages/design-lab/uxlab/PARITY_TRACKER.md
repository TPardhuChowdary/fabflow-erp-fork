### 1. Customers — PARITY VERIFIED (2026-08-30)
Source: `pages/Customers.tsx` (643 lines), read in full.

**List screen:**
- Header: "Customers" + live count ("{n} registered customers")
- "+ Add Customer" button (create-permission gated)
- Search input (filters by name OR contactPerson, case-insensitive)
- Table columns: Company Name, Contact Person, Phone, Email, GSTIN, State (name + code), Actions
- Row actions: Edit (pencil icon, edit-permission gated), Delete (trash icon, delete-permission gated), View History (clock icon, opens customer document history)
- Empty state: "No customers found"
- Access-denied screen for users without view permission

**Create/Edit dialog** (same dialog, `editing ? "Edit Customer" : "New Customer"`):
- Company Name * (required, inline validation, error clears on edit, autofocuses on validation failure)
- Contact Person, Phone, Email, GSTIN, State Name, State Code (single-line fields)
- Address (full-width textarea-style field)
- **Multi-email system**: dynamic array of {email, type}; type is a dropdown (Purchase/Accounts/Sales/Other); each row has a "Set Primary"/"✓ Primary" toggle button and a remove button; "+ Add Email" button
- **Additional Details**: dynamic array of {key, value} free-form pairs, each removable; "+ Add Detail" button
- Cancel / Save buttons; Save shows "Saving..." while in flight (real async simulated here since there's no backend)

**Delete flow:**
- A **linked-record guard runs before the confirm dialog is even shown**: blocks deletion with a toast error if the customer has any quotations, invoices, or projects referencing it — the confirm dialog never appears in that case
- If clear, shows a real confirm dialog ("Delete customer? Customer "X" will be permanently deleted.") before deleting

**Adapted in the prototype** (WHERE/HOW changed, nothing removed):
- No real backend, so create/update/delete are simulated against the mock store with the same validation/guard logic, not routed through `customersApi.ts`
- "View History" opens the existing `CustomerWorkspace` (which already shows the customer's quotations/projects/invoices inline) rather than a separate History page — a legitimate presentation change, not a removal, since the same information is reachable
- Permission gating uses the prototype's own role system instead of `canCreate`/`canEdit`/`canDelete`, but the gating behavior (hide the button if the role can't do it) is preserved
